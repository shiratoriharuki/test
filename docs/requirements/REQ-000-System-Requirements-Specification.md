## 1. 目的

このドキュメントは、勤怠管理システムのシステム要件を定義します。本システムは、従業員の出退勤時刻や休暇申請、カレンダーを用いた勤怠管理を可能にします。

### 1.1 ドキュメントの適用範囲

本ドキュメントは、勤怠管理システム開発に必要な主要機能要件、基本的な非機能要件、およびシステム制約を対象とします。

### 1.2 想定読者

- 開発チームメンバー
- プロジェクトマネージャー
- ビジネスステークホルダー
- 品質保証チーム

---

## 2. システム概要

### 2.1 システムの目的

勤怠管理システムは、従業員が日々の勤怠を記録し、休暇申請を行い、直感的なカレンダー UI で勤怠記録を参照できる Web ベースのソリューションを提供します。

### 2.2 主要機能

- カレンダーベースの勤怠管理インターフェース
- 勤務時間入力（出勤・退勤時刻の記録）
- 休暇申請管理（病欠、私用外出、出張 等）
- 勤怠レコードの保存と参照
- システムヘルスチェック

### 2.3 対象ユーザー

- **従業員**: 勤怠入力および休暇申請を行う主利用者
- **システム管理者**: システム保守と監視を担当する利用者

## 3. ハードウェアおよびソフトウェア構成

### 3.1 ハードウェア構成

#### 3.1.1 開発環境

**最小要件:**

- CPU: 4 コア、2.5GHz 以上
- メモリ: 8GB RAM
- ストレージ: 空き容量 50GB
- ネットワーク: インターネット接続

#### 3.1.2 本番環境

**想定スペック:**

- Web / アプリケーションサーバー: 4 コア以上、16GB RAM、SSD ストレージ
- データベースサーバー: 8 コア以上、32GB RAM、バックアップ付き SSD
- ネットワーク: 安定したインターネット接続

### 3.2 ソフトウェア構成

#### 3.2.1 技術スタック

**フロントエンド:**

- React 18 以降
- TypeScript
- Vite（ビルドツール、開発サーバー）
- 最新 Web ブラウザーをサポート（Chrome、Firefox、Safari、Edge 最新版）

**バックエンド:**

- Spring Boot 3.2 以降
- Java 21
- Spring Data JPA（ORM）
- Maven 3.8 以降（ビルドツール）
- RESTful API アーキテクチャ

**データベース:**

- PostgreSQL（本番環境、開発環境）
- 同時実行トランザクションをサポート
- Docker Compose によるローカル環境構築

**テスト:**

- JUnit 5（バックエンド単体テスト）
- Testcontainers（バックエンド結合テスト用 PostgreSQL コンテナ）
- Playwright（フロントエンド・バックエンド統合シナリオテスト）
- Cucumber（Gherkin 形式によるテストシナリオ定義）
- JaCoCo（コードカバレッジ測定）

## 4. 機能要件

### 4.1 業務フロー

#### 4.1.1 基本的な勤怠フロー

1. **システムアクセス**: 従業員が Web ブラウザーから勤怠システムにアクセスする
2. **日付選択**: 従業員がカレンダー UI から日付を選択する
3. **勤務時間入力**: 従業員が出勤・退勤時刻を入力する
4. **休暇管理**: 従業員が各種休暇を登録する
5. **データ保存**: システムが勤怠情報を保存し、後日参照できるようにする

### 4.2 ユースケース

#### 4.2.1 UC001: システム起動

**アクター:** ユーザー  
**概要:** ユーザーが勤怠システムにアクセスする **フロー:**

1. ユーザーがシステム URL にアクセスする
2. システムがカレンダーを含むメイン画面を表示する
3. ユーザーが勤怠操作を開始できる

#### 4.2.2 UC002: カレンダー操作

**アクター:** 従業員  
**概要:** 従業員が勤怠管理のために日付を選択する **フロー:**

1. 従業員がカレンダー画面を表示する
2. 従業員が任意の日付を選択する
3. システムが選択日付に応じた操作オプションを提示する

#### 4.2.3 UC003: 勤務時間入力

**アクター:** 従業員  
**概要:** 従業員が日々の勤務時間を記録する **フロー:**

1. 従業員が日付を選択する
2. 従業員が出勤時刻と退勤時刻を入力する
3. システムが入力値を検証し、勤怠情報を保存する

#### 4.2.4 UC004: 休暇登録

**アクター:** 従業員  
**概要:** 従業員が休暇申請を登録する **フロー:**

1. 従業員が日付を選択する
2. 従業員が休暇区分を選び、メモを入力する
3. システムが休暇情報を保存する

### 4.3 業務ルール

#### 4.3.1 勤務時間入力ルール

- 出勤時刻は退勤時刻より前であること
- 時刻は有効な HH:MM 形式で入力すること
- 未来日付の入力を許容する
- 従業員と日付の組み合わせごとに 1 件の勤怠レコードとする

#### 4.3.2 休暇管理ルール

- 対応する休暇種別: Sick Leave、Personal Leave、Business Trip
- 任意の日付に休暇を登録できる
- 既存の休暇レコードは変更および削除が可能

### 4.4 エンティティ

#### 4.4.1 勤怠レコード

**主要データ項目:**

- 従業員 ID（必須）
- 勤怠日（必須）
- 出勤時刻（任意）
- 退勤時刻（任意）
- ステータス（出勤・欠勤・休暇区分など）
- 備考（任意）
- レコード管理用タイムスタンプ

### 4.5 その他要件

#### 4.5.1 ユーザーインターフェース

- 最新ブラウザーで利用できる Web ベースのインターフェース
- 日付選択用のカレンダービュー
- 勤務時間入力および休暇申請フォーム

#### 4.5.2 データ管理

- 勤怠レコードの永続化
- ユーザー入力のバリデーション
- 基本的なレポート機能

## 5. 非機能要件

### 5.1 業務処理量条件

- **想定ユーザー数**: 初期は同時接続 50～100 名を想定
- **日次トランザクション**: 一般的な日次勤怠処理を円滑に処理できること
- **データ蓄積**: 勤怠レコードの継続的な蓄積を想定

### 5.2 性能条件

- **応答時間**: Web ページが実用的な時間内に表示されること
- **可用性**: 営業時間内はシステムが利用可能であること
- **データ処理**: 標準的な勤怠操作を効率的に処理すること

### 5.3 信頼性条件

- **データ整合性**: 勤怠データを損失なく保持すること
- **エラーハンドリング**: 利用者に分かりやすいエラーメッセージを表示すること
- **システム復旧**: 基本的なバックアップおよびリカバリー手段を備えること

### 5.4 セキュリティ条件

- **データ保護**: 従業員勤怠情報を適切に保護すること
- **アクセス制御**: 権限を持つユーザーのみがアクセスできること
- **通信保護**: 安全な通信プロトコルを利用すること

### 5.5 外部連携条件

- **API 設計**: 内部コンポーネント間連携のための RESTful API
- **データベース連携**: 標準的な DB 接続方式を利用すること
- **将来拡張**: HR システム等との連携拡張を想定すること

### 5.6 移行条件

- **データ移行**: 既存勤怠データがある場合は移行計画を策定すること
- **システム移行**: 既存システムからのスムーズな切り替えを実施すること

### 5.7 保守運用条件

- **システム監視**: 稼働状況の監視とヘルスチェックを行うこと
- **保守作業**: 定期的なシステム保守手順を整備すること
- **ドキュメント**: 運用担当者向けドキュメントを整備すること

### 5.8 拡張性条件

- **ユーザー増加**: ユーザー数の増加に対応できること
- **性能拡張**: 必要に応じて負荷に対応できるスケーラビリティを確保すること
- **機能拡張**: 将来的な機能追加を想定したアーキテクチャを採用すること

## 6. テスト方針

### 6.1 テスト自動化方針

本システムにおける品質確保のため、以下のテストレベルを定義し、全てのテストを自動化することを基本方針とする。

### 6.2 バックエンド単体テスト

バックエンドのビジネスロジック、ユーティリティ処理を対象とし、JUnit により自動実行可能な単体テストを実施する。正常系および異常系のテストケースを網羅し、C1（ブランチカバレッジ）80％以上を基準とする。

### 6.3 バックエンド結合テスト

アプリケーションとデータベース間の連携を対象とし、Testcontainers により起動したデータベース環境上で結合テストを実施する。スキーマは本番環境と同一のマイグレーションを適用して構築し、CRUD処理およびトランザクション制御の検証を自動的に行う。テスト間の独立性を確保すること。

### 6.4 フロントエンド・バックエンド統合シナリオテスト

主要業務フローを対象とした統合シナリオをGherkin形式で定義し、当該シナリオを基にPlaywrightによるE2Eテストスクリプトを生成・実行する。画面操作、画面遷移、バックエンドAPI連携を含む一連の処理を自動テストで検証する。

### 6.5 リリース条件

本方針に基づき、単体テスト、結合テスト、統合シナリオテストの全レベルについて自動化を徹底し、全テスト成功をリリース条件とする。

## 7. 用語集

### 7.1 業務用語

**勤怠レコード:** 特定の日付における従業員の出勤・欠勤状況を示すレコード。

**出勤時刻:** 従業員が勤務を開始した時刻。

**退勤時刻:** 従業員が勤務を終了した時刻。

**休暇申請:** 従業員が特定期間の休暇を申請すること。

**カレンダービュー:**
勤怠情報をカレンダー形式で表示するユーザーインターフェース。

### 7.2 技術用語

**API:** システム間連携を行う Application Programming Interface。

**フロントエンド:** アプリケーションのユーザーインターフェース層。

**バックエンド:** サーバーサイドのアプリケーションロジックおよびデータ処理層。

**データベース:** 勤怠レコードを保存するデータストア。

**REST:** Web サービス設計のためのアーキテクチャスタイル。

### 7.3 システムステータス値

**Present:** 指定日に勤務している状態。

**Absent:** 承認済み休暇なしで不在の状態。

**Sick Leave:** 病気を理由とした欠勤。

**Personal Leave:** 私的理由による欠勤。

**Business Trip:** 出張による不在。
